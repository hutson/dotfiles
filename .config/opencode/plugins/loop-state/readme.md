# loop-state

Appends a state diagram of the engineering loop to the session sidebar of loop sessions: phases 0 through 8 as a vertical chain (the grade gate chain nested under `7 grade`), each phase line naming the agent that does that work (the `7 grade` line shows the round counter instead, and its gate lines name the graders), plus a mark: `✓` done, `▶` current, `●` running (a worker attributed to that line has an active session; `●x2` means two running workers on one line), and `PASS` or `↺n` gate marks taken from the newest completed `Round <n>:` line in the goal file's `## Status` section, where `↺n` means that gate failed and the loop returned to node `n` (a `test-immutability` tripwire re-routes the quality-assurance mark to `5` instead of `6`). A running worker's `●` replaces that gate's stale mark. A legend and three short notes define the marks, what active time on a stage line means (question waits and pauses excluded), what a round is, and when `test-design` re-runs.

Each stage line and gate line with a recorded usage also carries a compact active-time total (`45s`, `12m`, `1h30m`), and the line for the current stage grows while the loop works. The metric is active agent time, not wall clock: the plugin reads the loop family's message records and takes the union of assistant-message activity spans (a span runs from `time.created` to `time.completed`, falling back to `time.streamed`, then to now, so an in-flight message still counts) minus the spans of `question` tool waits (`time.ran` or `time.created` to `time.completed`, falling back to now), so human answer time and idle pauses never count; merging the spans before subtracting is what keeps parallel workers on one stage from double-counting the seconds they share. The spans are attributed to a stage by which `## Timeline` window (`skills/loop/references/goal-file.md`) the message's `time.created` falls in, so re-entries of a stage accumulate into that stage's total. Token counts are summed over the same windows. The plugin, not the supervisor, does the arithmetic because nowhere else in the loop can token counts be observed: a subagent's return carries no usage and the supervisor's shell allowlist has no API access.

The results also land in `~/.opencode/progress/<name>-stage-usage.json`, one entry per loop, written from the same poll that recomputes them (so an unfocused tab keeps accounting) and only when the payload's `stages` and `total` actually changed. Each stage entry carries `activeMs`, `active` in `HH:MM:SS`, and the five token fields (input, output, reasoning, cache read, cache write), and `total` sums them; `stages` holds the eleven vocabulary stages, and an unknown timeline id is never serialized. The exit retrospective reads this sidecar and transcribes it verbatim into `~/.opencode/progress/loop-improvements.md` under `## Stage usage` (`references/improvement.md` defines the record); a loop that exits with no sidecar, as a headless run leaves, records `not recorded` rather than a recomputed guess. The file holds only times and token counts (never message content), and it is the goal-file filter that makes this safe: sidecars are `.json`, and only `*.md` entries are read as goal files.

The current phase comes from the goal file's `- State:` field (see `skills/loop/references/goal-file.md` for the vocabulary). The goal file is found by link, not by name: the supervisor records its own session id (from `printenv OPENCODE_SESSION_ID`) in the file's `- Session:` field at creation and updates it whenever `/resume` continues the loop in a new session, and the widget shows a file when that id names the viewed session or a member of its family, ranked by `/resume`'s rule among the family's linked files (the strictly newest ranking `Updated:` stamp wins; a tie shows an ambiguity note instead of guessing; a lone candidate is shown even when its stamp does not rank, because a passive widget has nothing to ask). Name-prefix lookup is gone by design: a loop started at an umbrella directory (several sibling repositories under one working directory) names its goal file after the deliverable rather than the root, and prefix matching silently showed nothing for it (the 2026-11-06 pinbump bootstrap loop, invisible in the sidebar at `/var/home/hutson/workspace`). Nothing renders unless the viewed session's family contains a `supervisor` session: `/loop`, `/resume`, and `/save` all select that agent and dispatched workers share its family, so outside a loop there is neither diagram nor warning. Inside a loop whose family no goal file links, the widget shows a short `loop: no goal file` line rather than hiding silently, because the silent absence was the original failure. Agent-written strings are never rendered raw: a `State:` value outside the id charset shows as `state: <invalid>`, file names violating the documented `^[A-Za-z0-9_-]+$` contract are skipped, a `- Session:` value outside `^ses_[A-Za-z0-9]{1,64}$` links nothing, and an unrecognized `session.status()` shape counts as not running, so live `●` badges fail closed rather than wrong; if the family API itself fails, the set holds only the viewed session, so the gate and link fail closed (nothing shows) rather than matching another loop. Live badges come from the viewed session's family status, so a worker that is dispatched but whose phase transition is not yet written still shows, and any running agent outside the vocabulary (for example `explore`) badges the current line.

The sidebar stays hidden at rest: `session.sidebar` remains `hide` in `cli.json`, and the first sighting of a loop in a TUI reveals it, once per session family per TUI process (`/loop` is when the human starts watching). `session.sidebar.toggle` (default `<leader>b`, so `ctrl+x` then `b`) still works by hand in both directions. The reveal is a flip, so it first reads the toggle command's live title (`Hide sidebar` means already shown, `Show sidebar` means hidden) and skips the dispatch when the sidebar is open; an unrecognized command shape degrades to one bounded flip per family rather than a flip on every render. The once-per-family decision is kept in TUI plugin memory storage so it survives plugin reloads (a config save or `/reload` previously re-armed the flip and closed the sidebar again), marks whole session families rather than a single root id because `session.root()` resolves late over the session cache, and never fires while the pane views a subagent session, where the host cannot show the sidebar at all. Because the host's toggle persists `session.sidebar: "auto"` to `cli.json` when it opens the panel, the reveal rewrites that single value back to `hide` about a second later, keeping the hidden-at-rest default without touching the file's formatting. Keeping the vocabulary and the link in sync is deliberate: a phase change needs matching edits in `skills/loop/SKILL.md`, its `references/goal-file.md`, and this plugin's node table, and the `- Session:` link spans `goal-file.md` (the field), `SKILL.md` (the recording rule), `agents/supervisor.md` (the exact `printenv OPENCODE_SESSION_ID` shell form), and this plugin's `sessionIdPattern`. The timeline is the same kind of coupling across five files: `goal-file.md` holds the `## Timeline` spec, `SKILL.md` holds the recording rule and the `date -u +%Y-%m-%dT%H:%M:%SZ` form, `agents/supervisor.md` holds the matching `date` permission and its pattern comment, `commands/resume.md` and `goal-file.md` carry the allowlisted-command count that permission produces, and this plugin's `parseTimeline` and node table read the stamps and own the stage vocabulary the sidecar serializes, so a phase change or a stamp-shape change is an edit to all of them at once.
